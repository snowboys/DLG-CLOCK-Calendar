# 11 浏览器 Web Bluetooth 对时与校准

`web/index.html` 是一个**自包含、无 CDN 依赖**的单页工具，移植自
[tpunix/HMCLOCK](https://github.com/tpunix/HMCLOCK) 的 HMWEBCTRL 对时功能，
适配本仓库的独立万年历固件。

它做的事只有一件：**连上价签 → 写一次 `0x91` 把正确时间灌进去 → 断开**。
不常驻、不开机自启、不采集任何电脑数据。价签随后凭本地 RTC 独立走时。

---

## 1. 打开页面

Web Bluetooth 要求 **安全上下文**：

| 环境 | 是否可用 |
|---|---|
| `https://<user>.github.io/<repo>/web/`（GitHub Pages） | ✅ 推荐，手机 / 电脑都能开 |
| `http://localhost:8000` | ✅ 本地开发 |
| `file:///.../web/index.html` | ❌ 不是安全上下文 |
| HTTP 局域网地址（如 `http://192.168.x.x`） | ❌ |
| iOS Safari / Firefox | ❌ 不支持 Web Bluetooth |
| 桌面 Chrome / Edge、Android Chrome | ✅ |

本地起服务：

```bat
python -m http.server 8000 -d web
:: 浏览器打开 http://localhost:8000
```

部署到 GitHub Pages 时把 Pages 源设为分支根目录即可，页面地址是
`https://<user>.github.io/<repo>/web/`（分支根目录下的整个目录树都会被发布）。

## 2. 使用步骤

1. 点 **「连接设备」** → 浏览器弹出设备选择框，选 `DLG-CLOCK-xxxx`。
   - Windows 上的 Realtek 蓝牙适配器服务发现可能要 20~30 秒，属于正常现象。
2. 连接成功后页面显示：设备名称、当前电压、设备时间、系统时间、两者秒差、对时后运行分钟数。
3. 点 **「同步时间」**：页面等到整秒，把当前系统时间打包成 `0x91` 写入 `0xFF01`。
   固件立刻重算农历 / 星期 / 节气 / 节日并写入 SPI Flash，随后页面回读确认。
4. 点 **「断开连接」**（或直接关页面）。价签继续独立走时。

**「刷新时间」** 只重新读一次设备时间，不改动任何东西。

## 3. 时间校准（`0x92`）

晶振会有 ppm 级误差，跑几个月能差出几秒到几十秒。校准流程（与 HMWEBCTRL 原版一致）：

1. 读取 `cal_minute`（距上次对时经过的分钟数）。
   - `-1` = 从未对时 → 提示先同步时间
   - `< 2880`（不足 2 天）→ 样本太短，拒绝校准
2. 轮询 `0xFF01`，等设备**分钟跳变**。
   > 固件在 BLE 连接期间每秒把当前时间写回 `0xFF01`（`clock_push()`），
   > 所以 `readValue()` 拿到的是实时走时的值，而不是写入回显。
3. 比较「设备跳变时刻」与「系统跳变时刻」，算出秒差 `diff`（设备快了为正）。
4. 写 `92 <diff_lo> <diff_hi> 00`（有符号 int16 小端）。固件按
   `diff / cal_minute` 调整 1 秒节拍，长期抵消漂移，并把 `cal_minute` 归零。

> 校准值保存在 RAM，断电后丢失；需要长期精度就每隔一两个月校准一次。
> 固件对 `cal_minute <= 0` 做了保护，避免除零触发 HardFault。

## 4. 协议细节

### GATT

| 项 | UUID | 属性 |
|---|---|---|
| 主服务 | `0000ff00-0000-1000-8000-00805f9b34fb` | 自定义服务 |
| 长值特征 | `0000ff01-0000-1000-8000-00805f9b34fb` | Read / Write Request |
| 电压 | `0000ff02-0000-1000-8000-00805f9b34fb` | Read（uint16 小端，单位 mV） |
| 控制点 | `0000ff03-0000-1000-8000-00805f9b34fb` | Write |

Web Bluetooth 可以直接用 16 位短 UUID：`getPrimaryService(0xff00)`、
`getCharacteristic(0xff01)`；`requestDevice` 里要写 `optionalServices: [0xff00]`。

### `0x91` 同步时间（写入 `0xFF01`）

最少 8 字节；本页面按 HMCLOCK 原版发 12 字节，多出的 4 字节本固件忽略。

| 字节 | 内容 |
|---|---|
| `[0]` | `0x91` |
| `[1..2]` | 年，uint16 小端（2026 → `EA 07`） |
| `[3]` | 月，**0-based**（0=1月 … 11=12月） |
| `[4]` | 日，1-based |
| `[5]` | 时 |
| `[6]` | 分 |
| `[7]` | 秒 |
| `[8]` | 星期（0=周日），HMCLOCK 原版字段，本固件忽略 |
| `[9]` | 农历年 − 2020，忽略 |
| `[10]` | 农历月（含闰月高位），忽略 |
| `[11]` | 农历日，忽略 |

例：**2026-11-19 09:30:00** → `91 EA 07 0A 13 09 1E 00`（8 字节即可）

```
91 EA 07 0A 13 09 1E 00 04 06 09 0B   ← 页面实际发的 12 字节（后四字节仅兼容原版固件）
```

> 为什么农历字段可以随便填：本固件的 `clock_set()` 只取前 8 字节的公历，
> 然后调用 `cal_sync_date()` 用内建农历表 / 节气表 / 节日表重算，不需要上位机提供农历。

### `0xFF01` 回读（13 字节）

| 字节 | 内容 |
|---|---|
| `[0..1]` | 年，uint16 小端 |
| `[2]` | 月，0-based |
| `[3]` | 日，1-based |
| `[4..6]` | 时 / 分 / 秒 |
| `[7..10]` | `cal_minute`，int32 小端（`-1` = 从未对时） |
| `[11..12]` | 当前时钟修正值（int16 小端低 16 位） |

刚写完 `0x91` / `0x92` 的瞬间，`readValue()` 可能先返回写入回显；固件 1 Hz 的
`clock_push()` 会在 1 秒内覆盖它，页面对此做了自动重试（最多 5 次 × 400 ms）。

### `0x92` 时间校准

| 字节 | 内容 |
|---|---|
| `[0]` | `0x92` |
| `[1..2]` | 秒差，有符号 int16 小端（负数 = 设备慢了） |
| `[3]` | `0x00` |

## 5. 不用网页的替代方案

**手机 nRF Connect**

1. 扫描并连接 `DLG-CLOCK-xxxx`
2. 展开服务 `0000ff00-...`，找到 `0000ff01-...`
3. 选择 Write / Write Request，类型选 `BYTE ARRAY`，写 `0x91` 包（见上例）
4. 断开即可

**电脑一次性脚本**

```bat
python tools\sync_time.py                    :: 自动扫描
python tools\sync_time.py 18:BC:5A:5A:22:CA :: 指定 MAC，更快
python tools\sync_time.py --nrf-help         :: 打印手机手动写法
python tools\sync_time.py --reset-bt         :: Windows 蓝牙适配器卡住时关/开 6 秒复位
```

`sync_time.py` 用 `bleak`，连接完成后会做一次「精确二次校准」，
抵消 Windows 上 GATT 服务发现耗时带来的秒级误差。

## 6. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 「连接设备」按钮灰色 | 页面不是 HTTPS/localhost，或浏览器不支持 Web Bluetooth |
| 设备选择框里找不到设备 | 价签未上电、已被别的主机连上、或蓝牙未开启；断开其它连接后重试 |
| 连接后卡很久 | Windows Realtek 适配器服务发现慢，等 20~30 秒 |
| 设备时间不跳 | 固件版本过旧（未启用连接期间每秒 `clock_push()`），重新烧录本仓库固件 |
| 校准提示「样本太短」 | 对时后不足 2 天，属正常保护，过几天再校准 |
| 断电很久后时间不对 | DA14585 无掉电保持 RTC，只能恢复到最后一次快照；重新对时一次即可 |
