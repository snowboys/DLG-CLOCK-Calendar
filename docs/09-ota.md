# 09 蓝牙 OTA 升级

不用拆机、不用 J-Link，直接用蓝牙把新固件推给副屏。约 20 秒。

## 1. 怎么用

```bat
:: 1) 先编译出新固件 (产物 firmware\pcmonitor\build\pcmonitor.bin + pcmonitor.json)
cd /d <SDK>\projects\target_apps\ble_examples\pcmonitor
python build.py

:: 2) 推给副屏 (会自动暂停后台推送, 升级完再恢复)
python tools\ota.py
python tools\ota.py 18:BC:5A:38:28:81              :: 指定 MAC, 省去扫描
python tools\ota.py --bin firmware\release\pcmonitor_middle.bin
```

- 升级前请关闭上位机 `PcMonitorGUI`（它占用 BLE 连接）。
- 结束后工具会自动重启后台推送并重新连一次设备，确认新固件活着。
- 想留在"接管模式"调试就加 `--keep-agent`。

正常输出：

```
镜像  : 56112 字节, version=0xA5DB97D2, crc=0xF02C0F44
包大小: 56320 字节 / 220 页
 100%  220/220 页  18.4s
发送完成, 提交校验 ...
等待设备重启 ...
升级完成: 设备已重启并接受数据
```

## 2. Flash 布局

```
0x00000  引导镜像 (原厂/工厂)
0x04000  槽 A: 64 字节 0x7051 头 + 镜像
0x1F000  槽 B: 64 字节 0x7051 头 + 镜像
0x38000  产品头: 70 52 ... 记录槽 A/B 的地址
0x39000  EPD 参数
0x3B000  用户配置 (见 06-config)
```

槽头 64 字节：

| 偏移 | 内容 |
|---|---|
| `+0` | `70 51 AA` + **序列号**（第 4 字节，越大越新，`FF`=无效） |
| `+4` | 镜像长度 |
| `+8` | 镜像 CRC（算法同固件 `crc32(0, ...)`） |
| `+28` | 版本号（`build.py` 按源码内容生成） |

引导器每次上电比较两个槽的序列号，启动数值大的那个。`selflash()` 也会在版本不一致时把
运行中的固件写进另一个槽，同样用序列号 +1。

## 3. 协议

写入特征 `0000ff01-...`（现有长值特征，不需要额外服务），每包 ≤ 136 字节。

| 命令 | 包格式 | 作用 |
|---|---|---|
| `0xA0` | `A0 00 00 00` + size(u32) + version(u32) + crc(u32) | 开始：选非活动槽、擦除 |
| `0xA2` | `A2` + 7 字节保留 + 128 字节 | 页前半 |
| `0xA3` | `A3` + 7 字节保留 + 128 字节 | 页后半，凑满 256 字节写一页 |
| `0xA4` | `A4 00 00 00` | 结束：长度 + CRC 校验 |

传输顺序：槽头(64B) + 镜像，按 256 字节补 `FF` 对齐。

## 4. 为什么不会变砖

- **第 0 页（含槽头）最后才写**。传输中槽内序列号仍是 `FF`（无效），
  中途断连、掉电、蓝牙超时，引导器还是启动旧槽 —— 副屏最多黑一下。
- `0xA4` 时固件把收到的字节数和 CRC 与主机声明值比对，**不一致就不提交**，
  并且不会复位，旧槽继续用。
- 提交前还会把序列号、长度、CRC、版本号一起写进槽头，避免主机和固件对不上。

## 5. 升级失败怎么办

| 现象 | 原因 | 处理 |
|---|---|---|
| 连不上设备 | 后台推送/上位机占用连接 | 关掉上位机；确认 `schtasks /Query /TN PcMonitorAgent` 已停 |
| 传到一半失败 | 蓝牙干扰、设备被拿走 | 直接重跑，槽内是无效镜像，不会影响旧固件 |
| 提交后黑屏 | 新镜像本身有问题 | 用 `python tools\flash.py` 经 J-Link 烧回旧固件（A/B 双槽，旧槽仍在） |
| `MTU` 太小 | 系统没协商出大 MTU | Windows 一般没问题；打印里 MTU < 139 就要换主机 |
